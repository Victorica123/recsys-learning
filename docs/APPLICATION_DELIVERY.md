# 本轮交付验证：从推荐到反馈

依据网页版 GPT《评审改进路线》和 [PR #1](https://github.com/Victorica123/recsys-learning/pull/1)，
本轮优先完善视频 / 内容推荐应用的交互、接口可靠性和部署验证。使用已有 MovieLens 权重。

## 先看能演示的变化

- 网页直接调用 v1 API，选用户、生成推荐、点击“感兴趣”在一页完成。
- 内容进入视口才记录曝光；点击前确保曝光已保存。失败后沿用事件编号重试。
- API 补齐输入校验、错误响应和 OpenAPI；空推荐保持统一返回结构。
- CPU 容器实际构建并运行，模型只读挂载，反馈存入持久卷；重建后数据保留。

主入口见 [15 分钟导学](../项目导学.md)，机器可读结果见
[验证参考 JSON](../artifacts/application_delivery_reference.json)。关键结果已随仓库提交，
原始逐次报告保留在本地 `experiments/`，无需这些本地文件也能查看本页与参考 JSON。

## 一个适合面试演示的故障

固定用户 1，生成 5 条推荐。脚本分别重试曝光和点击，最终只增加 **1 个推荐批次、5 条曝光、1 条反馈**。
缺少曝光的点击和内容冲突的事件都被拒绝。

浏览器还模拟了“服务器已保存点击，但响应在途中丢失”：页面显示中文错误和“重试反馈”；
重试请求的内容、时间和事件编号均保持一致，API 返回 `duplicate=true`，数据库仍只有一条点击。
这可以用来讲清：**客户端保留事件身份，数据库负责幂等，页面负责让用户恢复操作。**

窄屏页面已检查并修复类型文字换行。可见性实验中，10 条推荐最初只记录了视口内的 4 条，
滚动后才达到 10 条曝光。以上操作均为隔离数据卷中的测试流量。

## 实际容器结果（2026-09-14）

环境：Windows 客户端访问 Docker Desktop Linux 容器，6 个逻辑 CPU、约 16 GiB 内存，
Python 3.12.14、Torch 2.9.1 CPU，2 个 worker，SQLite/WAL 位于命名数据卷。
测试使用同一用户 1、`k=10`，每组预热 10 次后发出 200 次 POST 请求。

| 配置 | 并发 | HTTP 200 / 429 | 成功 RPS | 成功请求 p95 | 成功请求 p99 |
|---|---:|---:|---:|---:|---:|
| 默认保护 | 1 | 173 / 27 | 81.66 | 7.06 ms | 8.81 ms |
| 默认保护 | 16 | 74 / 126 | 166.83 | 32.82 ms | 44.13 ms |
| 容量测量 | 1 | 200 / 0 | 183.10 | 6.94 ms | 8.54 ms |
| 容量测量 | 16 | 200 / 0 | 376.49 | 84.40 ms | 237.23 ms |

默认保护：每 worker 并发上限 8、速率 80/秒、突发 8；容量测量：并发上限 32、关闭速率限制。
单连接通常固定在一个 worker，所以默认并发 1 主要受一个 80/秒令牌桶约束。
这些短时测量说明吞吐与尾延迟的取舍，不能直接当作持续负载容量或公网 SLO。

所有压测都没有 5xx、连接异常或请求编号丢失；表中的 429 均为速率限制。
另一次突发冒烟也触发了并发保护：233 次 `rate_limited`、1 次 `overloaded`。
低速阶段 40/40 成功，两个 worker 均处理了推荐，计数、Prometheus 和资源指标一致。
该次采样的两 worker RSS 合计约 1.10 GiB，属于一次采样而非内存峰值。

## 保留的一组模型对照

复用已有 ML-1M 端到端实验（3,552 个用户，逐用户留一、Top-10）：

| 服务策略 | Recall@10 | 当前用途 |
|---|---:|---|
| 双塔直接推荐 | 0.097973 | 默认策略 |
| 双塔召回 50 → 原 DeepFM 精排 | 0.065034 | 失败复现 |

精排减去基线的差值为 -0.032939，95% 区间为 [-0.044482, -0.021959]。
这组结果支持保留当前默认策略。它对应离线留一协议，存在跨用户时间穿越；全局时间切分的
双塔 Recall@10 约为 0.069，属于另一协议。解释见 [端到端评估笔记](../notes/15-端到端评估与精排重建.md)。

## 怎样复验

准备好数据、权重和 Python 环境后，从仓库根目录执行：

```powershell
docker compose up --build -d
.venv/Scripts/python.exe scripts/demo_recommendation_flow.py --tag delivery-demo-01
.venv/Scripts/python.exe scripts/production_smoke.py --base-url http://127.0.0.1:8000 --tag delivery-smoke-01
```

每次更换 `--tag`。外部冒烟检查正在运行的容器，不会另外启动或停止服务。
本轮实际使用隔离 Compose 项目 `recsys-review-20260914`、端口 8860；负载与浏览器事件不进入原本的本地反馈库。
压测入口是 `scripts/load_test_api.py --method POST`，完整参数和限流约定见 [运行手册](PRODUCTION_SERVING.md)。

代码检查使用 `scripts/ai_startup_harness.py --check`、`--test`、`--release`，
以及 CI 相同的 Ruff 错误检查和 `docker compose config --quiet`，均已通过。
按项目约定，集成测试需显式开启；本轮没有独立确认 GitHub 远端 CI 状态。
