# 推荐系统项目面试手册

## 先记住定位

这不是“实现了很多模型”的课程合集，而是一个围绕同一业务问题持续补齐的系统：

> 我独立完成了推荐系统从离线建模、两阶段在线推理、生产可观测性，到真实反馈
> OPE 决策的闭环；最重要的结果不是某个指标，而是用证据决定什么应该上线、
> 什么不应该上线。

## 60 秒版本

我做的是一个基于 MovieLens 的生产导向推荐系统。模型侧采用双塔加 Faiss 做
候选召回，DeepFM 做精排，并扩展了 SASRec、Bandit、会话强化学习和离线 RL。
过程中我遇到过双塔训练损失下降但召回不升的问题，最后定位到评估协议与采样
偏差，加入 logit 校正后 Recall@10 从 MF 的 0.062 提升到 0.098。

**最有价值的一段是后来补的端到端评估**：双塔 Recall 0.098、DeepFM AUC 0.754
两个分段指标都体面，但把它们串起来跑，端到端 Recall@10 只有 0.065，
**比不要精排还差 33.6%**。诊断发现精排把候选坍缩到了热门头部。我做了六版
重训修复（最后一版用 out-of-fold 交叉拟合特征），缺口补回 88.7%，但最好的
v6 仍与"不精排"统计上持平、区间跨 0，按门槛没有上线。

我还补了一组**评估协议对照**：既有的 Recall 0.098 来自 leave-one-out（存在
时间穿越），换成全局时间切分后是 0.069，两个区间不重叠。两个都报、标注差异。

工程侧，我把推理核心抽成同源服务，提供 Streamlit 和 Starlette API，完成多
worker、准入保护、限流、Prometheus、优雅停机和压测。本机 2 worker、并发 16
时成功吞吐约 270 RPS，HTTP 200 p99 约 72 ms。用 profiler 定位到推荐核心
40% 的时间花在 pandas 标量索引上（模型前向只占 8%），改成预展开 dict 后
核心延迟 4.69 ms → 1.66 ms → 当前默认路径 0.19 ms。

最后我实现曝光、反馈、propensity 和 IPS/SNIPS 评估。个人实验倾向低权重
多样性策略，但外部 1,834 人问卷显示高多样性会显著降低感知个性化，所以没有
为了“指标好看”全量上线，而是保留 DeepFM 基线，把多样性作为个性化候选。

## 5 分钟版本

### 1. 业务问题

目标是为用户从全量电影中返回 Top-K，同时兼顾相关性、延迟、多样性和长期体验。
单一模型难以同时解决全库计算成本和精细交叉特征，因此采用召回—排序分层。

### 2. 模型方案

- MF 是可解释基线，Recall@10 为 0.062。
- 双塔把用户与电影映射到同一向量空间，通过 Faiss 从 3,706 部电影召回 50 个
  候选。
- DeepFM 在已评分样本上学习正向偏好，AUC 为 0.754；这不是 CTR，且端到端
  实验后来证明它不适合默认重排双塔候选。
- SASRec 建模序列兴趣；Bandit 与会话 RL 研究探索—利用和长期疲劳。
- 参考 DeepEyes 的主动感知思想，把固定重排改成带调用成本的工具门控，并用
  group-relative REINFORCE / GRPO 与规则门控做对照。低工具成本区规则门控胜出；
  3-seed 成本扫描显示 cost≈0.5 是相变候选、cost=0.8 时学习策略均值更高；
  由于独立重复不足，尚不能宣称显著。
- **精排层目前是端到端净损失**（见 3.5）：原版显著劣于"不精排"，重训六版后
  最好的 v6 与"不精排"持平但未跨过晋升门槛。
- 召回指标有两个协议：leave-one-out 0.098（有时间穿越）、全局时间切分 0.069
  （无穿越），区间不重叠。引用时必须带协议名。

不要把不同数据集、负采样和评估协议下的指标横向比较。面试时主动说明这一点。

### 3. 最值得讲的故障诊断

双塔第一版训练 loss 正常下降，但 Recall 反而低于 MF。排查后发现：

1. 评估协议没有完全对齐；
2. 负采样改变了物品先验，原始 logit 不再等价于全库概率；
3. 热门物品与采样分布造成排序偏差。

修复方式是统一候选与留一法口径，并按采样概率做 logit 校正。Recall@10 提升到
0.098，相对 MF 提升 58%。这段故事用于证明“会诊断”，不是只会调用模型。

### 3.5 最值得讲的架构性发现（首推这一条）

补上端到端联合评估后发现，线上真实链路的指标是**负的**：

| 环节 | Recall@10 |
|---|---|
| 召回天花板 Recall@50 | 0.307 |
| 不精排（双塔 Top-10） | **0.098** |
| 端到端（召回 50 → 精排 10） | **0.065** |

精排增量 −0.0329，配对 bootstrap 95% CI [−0.0445, −0.0220]，**显著劣于不精排**。

根因诊断靠一个指标就定位了：**曝光集中度**。Top-10 里出现的不同电影数，
双塔是 1853 部，精排后只剩 773 部，最热 20 部占曝光从 17% 涨到 40%——
《辛德勒的名单》出现在 35% 用户的推荐里。**精排学到的是"电影好不好"
（item bias），不是"这个用户会不会喜欢"。**

这是典型的 **sample selection bias**：DeepFM 训练时只看用户主动评分过的
(user, item) 对，区分好片烂片就能拿 AUC 0.754；服务时却要对双塔筛出的 50 个
高相关候选打分，其中很多组合不在评分样本分布里；此时更需要用户级相关性。
同期补的 GAUC（0.735 < AUC 0.754）方向一致。

**六版修复，每版只改一件事**：

| 版本 | 改动 | Recall@10 | Δ | 判定 |
|---|---|---:|---:|---|
| v0 | 原版 | 0.0650 | −0.0329 | 显著更差 |
| v1 | 负样本换成召回候选 | 0.0769 | −0.0211 | 显著更差 |
| v2 | + listwise softmax | 0.0808 | −0.0172 | 显著更差 |
| v3 | + 用户-物品交叉特征 | 0.0870 | −0.0110 | 显著更差 |
| v4 | 负样本截到 serve_k=50 | 0.0774 | −0.0206 | **反而变差** |
| v5 | 残差：从复刻召回起步 | 0.0923 | −0.0056 | CI 跨 0 = 持平 |
| **v6** | **+ 4 折交叉拟合特征** | **0.0943** | **−0.0037** | **CI 跨 0 = 持平（最优）** |

四个可讲的点：

1. **v1 单项收益最大**，而且热门坍缩一步修好（去重物品 773 → 2308）——
   验证了根因诊断。
2. **v4 是我自己被实验否定的假设**。我以为负样本该截到线上真正面对的
   top-50，结果变差：隐式反馈里 top-50 含大量**假负样本**（用户会喜欢但
   没评分的电影），只用最难的负样本等于教模型压制好物品。难负样本要掺，
   不能全用。
3. **v5 的设计**：`score = w·tt_score + gate·deepfm_logit`，`gate` 初始化为 0，
   所以训练开始时输出与召回顺序完全一致，精排只能做增量，**最坏退化成召回
   本身而不是把它推翻**。v1~v4 都从与召回无关的随机初始化出发，得自己重新
   学出召回已编码的相关性——这是它们追不平基线的结构性原因。
4. **最有说服力的是最后那个诊断**：把 v6 的残差参数打出来，
   `w_retrieval=19.65`、`gate=−1.22`——**门控权重只有召回的 6%，而且是负的**。
   模型自己学出来的结论就是"基本照抄召回，并且把 DeepFM 分量当惩罚项"。
   这让我能下一个更强的结论：**这不是实现问题，是信息问题——在 ML-1M 上、
   用这套特征，精排没有召回不知道的信息。** 要赢必须给它召回看不到的东西
   （实时上下文、序列行为、多目标信号），而不是把同样的信息再学一遍。

**决策**：v0 立即下线（被证实的净损失）；v5/v6 都**区间跨 0，按门槛不晋升**；
线上直接用双塔 Top-10。若业务必须保留精排层，用 v6——缺口最小且不会主动
伤害指标。**注意："缺口补回 88.7%"是过程描述，不是效果结论**，不能说成
"基本追上了"。

细节见 `notes/15-端到端评估与精排重建.md`。

### 4. 生产化

`src/serving.py` 是单一推理事实源，供 Demo 与 API 复用。服务具备：

- live/ready 探针、请求关联 ID、结构化日志；
- 单 worker 准入控制和令牌桶，过载返回 429 + `Retry-After`；
- 多 worker 指标聚合、Prometheus、CPU/RSS/事件循环 lag；
- 压测脚本、生产冒烟和优雅停机竞态测试。

本机 1/2/4 worker 的 RSS 约为 0.89/1.78/3.55 GiB。面试结论应是：
扩 worker 能降低 p99、提高吞吐，但内存近线性增长，配置必须由 SLO 与成本共同决定。

### 5. 反馈与业务决策

服务记录完整候选池、实际曝光、行为策略概率和真人反馈。使用 item-inclusion
IPS/SNIPS、支持度、ESS 和 bootstrap 比较 DeepFM 与多样性重排。

个人 20 批试验给出约 +11.1% 的方向性信号，但只有一名体验者。随后引入
GroupLens Personality 2018 做外部一致性检查：中等多样性的观看意愿方向为正但
区间跨 0，高多样性显著降低感知个性化 0.332/5 分。最终不做全局替换。

### 6. Agentic 工具门控

智能体在“直接用 SASRec 推荐”和“调用疲劳感知重排工具”之间选择。300 个同种子
仿真会话中，规则增益门控以 87.2% 的调用率保持 17.947 的用户奖励，净奖励
16.203，高于始终调用的 15.947。学习策略 argmax 退化为 100% 调用，采样部署又
损失用户奖励；条件奖励消融也几乎无差别。因此最终保留框架和规则门控，不上线 RL。

**但后来我发现单成本点结论的适用范围可能被高估了。** 上面的 P0 规则门实验
使用 tool_cost=0.10；后续同预算 GRPO 对照使用 0.03，两者不能混报。再沿成本轴
扫 6 个点 × 2 算法 × 3 seed，得到以下探索性结果：

| tool_cost | 学出来的门控 − 规则门 | 旧 3-seed 描述区间 | 探索性方向 |
|---:|---:|---|---|
| 0.03 | −2.690 | [−4.99, −1.41] | 规则均值更高 |
| 0.30 | −1.294 | [−2.58, −0.58] | 规则均值更高 |
| 0.50 | −0.165 | [−0.80, +0.20] | **方向不稳定** |
| 0.80 | **+1.915** | **[+1.74, +2.19]** | **RL 均值更高；待复验** |

这 3 个 seed 上差距**单调收窄**，cost≈0.5 出现穿越零点的候选。原因很清楚：
**tool_cost=0.03 时工具几乎总是划算，最优解退化成"永远调用"，
"学会何时调工具"这个问题本身就不成立。**
RL 的价值只在决策边界真正复杂、固定阈值刻画不了的时候才出现。

这条的表述应该是："我发现低成本单点结论不能外推，扫轴后得到相变候选；但只有
3 个 seed，所以先加了推断护栏，等待 ≥10 seed 复验。" **单点实验和少量随机种子
得出的否定/肯定结论都不可靠。**

顺带一个实现细节值得讲：GRPO 的 `--epochs K=1` 时，重要性比恒等于 1、裁剪
永不触发，**梯度与 REINFORCE 逐位相同**（`torch.equal() == True`）。这解释了
论文为什么要冻结参考模型 + 多轮复用——不然你以为在跑 GRPO，实际在跑 vanilla
policy gradient。

## 面试官最可能追问

### 为什么不用 DeepFM 直接给全库打分？

它需要对每个用户—物品对构造交叉特征。两阶段架构用双塔把全库检索变成向量
近邻搜索，只对几十个候选运行更重的精排，隔离了吞吐与精度目标。

### AUC 0.754 能说明线上推荐好吗？

不能，而且我用实验证明了它不能。AUC 衡量的是采样分类任务的排序能力，
和 Top-K 链路质量不是一回事——本项目 DeepFM AUC 0.754 看着体面，但把它
接在双塔后面跑，端到端 Recall@10 比不接它还低 33.6%。补的 GAUC（0.735）
方向一致：全局 AUC 里有一部分区分度来自"哪些电影整体被打高分"，属于跨用户
信息，而线上体验取决于同一个用户内部的顺序。

### 为什么精排会比不精排更差？这不反直觉吗？

反直觉，但机制很清楚。精排的训练分布（用户主动评分过的 user-item 对）和
服务分布（双塔筛出的 50 个高相关候选）不一致。在训练分布上，"区分好片烂片"
就足以拿高 AUC；到了服务分布，候选普遍质量较高，需要的是用户级相关性，而模型没学过。
表现出来就是把候选坍缩到热门头部——Top-10 去重物品从 1853 掉到 773。

### 缺口都补回 88.7% 了，为什么还不上线？

因为 v6 的配对 bootstrap 95% 区间是 [−0.0132, +0.0053]，**跨 0**。跨 0 的
意思是这个差距可能就是噪声，我没有证据说它比不精排好。**"补回 88.7%"是
过程描述，不是效果结论**——这两者听起来很像，但一个是我做了多少工作，
另一个是用户拿到了什么。本项目对 OPE、对 RL、对精排用的是同一条门槛：
**区间不含 0 才允许宣称收益**。按均值符号下结论，和单跑一次就报 +4.8%
是同一种错误。

### 你试过 out-of-fold 特征吗？

试过，就是 v6。双塔用同一批交互训练过，它对训练正样本的打分是乐观偏置的；
精排把 tt_score 当特征学时，权重是在这个乐观分布上拟合的，到测试集就偏了
——这是叠加模型（stacking）的经典陷阱。我把训练交互切成 4 折，第 k 个双塔
只用其它 3 折训练，只给第 k 折的样本算特征，这样每个训练样本的 tt_score
都来自一个没见过它的模型，与线上"目标物品是未见过的"完全同构。

**结果：+0.0020，方向对但不够翻正。** 一个旁证是验证指标自己变诚实了——
去掉乐观偏置后同配置下验证 Hit@10 明显下降，说明之前那个漂亮数字里
确实有一部分是泄漏喂出来的。

### 六版都没翻正，你怎么判断该不该继续试第七版？

我让模型自己回答了这个问题。v6 的残差形式是
`score = w·tt_score + gate·deepfm_logit`，把学出来的两个标量打出来：
`w=19.65`、`gate=−1.22`——**门控只有召回权重的 6%，而且是负的**。

也就是说模型自学的结论是"基本照抄召回，并且把 DeepFM 分量当惩罚项用"。
这让我能下一个比"再调调看"强得多的判断：**这不是实现问题，是信息问题。
在 ML-1M 上、用这套特征，精排没有召回不知道的信息。**

要让精排真正有价值，必须给它召回看不到的东西——实时上下文、序列行为、
多目标信号、内容特征。所以下一步不是调精排，而是**把 SASRec 的序列表示接
进精排**（那是召回确实没有的信息），或者换一个有多目标信号的数据集。
这也解释了工业界的一条常识：精排的价值主要来自特征丰富度，而非模型复杂度。

### 你的 Recall@10 = 0.098 是怎么测的？

leave-one-out：每个用户按时间的最后一条评分做测试。**这个协议有时间穿越**
——用户 A 的测试时刻可能早于用户 B 的某些训练交互。我补了一组全局时间切分
（无穿越）作对照：**0.069 [0.055, 0.085]，与 leave-one-out 的区间不重叠**。

两个都报的原因是：leave-one-out 与 SASRec 复现、与项目既有全部结果可比，
换掉就没法纵向比；但只报它会高估。所以正确做法是两个都给、并标注差异，
而不是挑好看的那个。

要补充的是，29.4% 的差距里既有"消除时间穿越"，也有"时间切分训练数据更少、
任务更难"，这个实验拆不开——所以我不会说"leave-one-out 恰好高估了 29.4%"。

### logit 校正为什么有效？

负采样训练改变了正负样本的先验。未经校正的 logit 更接近采样分布下的后验，
会偏向采样概率高的物品；减去采样概率对应的偏置后，更接近目标全库排序。

### IPS 的关键假设是什么？

一致性、可忽略混杂和正支持。目标策略可能选择的物品必须在行为策略下有非零
曝光概率；否则 IPS 无法估计。权重过大还会导致高方差，因此同时检查 ESS。

### 为什么单人 bootstrap 区间会退化？

如果以 actor 为 cluster，而数据只有一个 actor，每次重采样都会抽到同一个完整
cluster，区间没有总体不确定性意义。因此个人结果只能作为个人信号。

### 为什么没有把多样性策略上线？

本地信号只代表一人；外部问卷没有证明普遍收益，且高多样性显著降低感知
个性化。业务上应保留基线，通过个性化权重或真实 A/B 再逐步放量。

### 为什么 CQL 反而不如 naive offline DQN？

当前仿真器回报有界、动作全合法且日志覆盖较好，CQL 要防御的严重外推误差没有
出现；保守惩罚反而压制了可学习动作。结论不是“CQL 无效”，而是算法先验必须
匹配数据覆盖和回报结构。

### 为什么 Agentic RL 没有胜过规则门控？

在 tool_cost=0.03 这个点上没胜过：仿真器直接给出了准确的工具前后点击概率，
工具成本又低到"几乎总该调用"，因此“预期增益大于成本”就是一个近乎解析的决策，
策略梯度面对随机点击只会增加方差。

3-seed 成本扫描提示这个结论可能只在低成本区成立：cost=0.8 时学习门控均值
高 +1.92，候选穿越点在 cost≈0.5；正式结论要等 ≥10 seed。**RL 的价值只在决策边界
真正复杂、固定阈值刻画不了的时候才出现**——低成本区最优解退化成"永远调用"，
"学会何时调工具"这个问题本身就不成立。

### 如果重做一次，优先改什么？

**第一件事：在写第二个模型之前，先把端到端评估建起来。**
这个项目分段指标全绿了很久，端到端却是负增量；修它花了六个版本（含 out-of-fold 交叉拟合），最好的
结果也只是打平。**修一个架构性错误的成本，远高于一开始就把评估做对。**

其次才是：真实线上随机实验、特征新鲜度和训练—服务一致性检查，
并将单机指标与限流迁移到跨主机基础设施。

### 429 为什么比排队好？

饱和后继续排队不会增加吞吐，只会放大尾延迟并耗尽资源。明确拒绝让调用方按
`Retry-After` 退避，保护已准入请求的 SLO。

### 为什么 SQLite 能支持多 worker？

单机最小闭环使用 WAL、短事务和幂等事件 ID。它适合当前吞吐和实验规模，但不是
跨主机事件流方案；生产扩展应迁移到消息队列和集中存储。

## 不能说过头的地方

- RL 指标来自冻结 SASRec 用户仿真器，不是真实线上留存。
- Agentic 工具的收益信号来自同一个仿真器，不能表述为真实流量节省或线上 uplift。
- 压测来自一台 Windows 主机，不代表云端或跨网络 SLO。
- 外部问卷的多样性处理不是当前 `diversity_weight=0.15` 的直接 A/B。
- 当前没有真实商业收入、Kafka/Spark 特征流水线或跨主机部署。
- 个人项目不能表述成“负责线上亿级系统”，应表述为“独立实现并验证本地闭环”。
- **不能说"我把精排修好了"**。六版之后最好的结果是与"不精排"**持平**
  （CI 跨 0），没有任何一版打败基线。正确表述是"我量出了负增量、定位了根因、
  把缺口收窄了 88.7%，并按证据门槛拒绝上线"。**"补回 88.7%"不能说成
  "基本追上了"**——前者是过程，后者是结论。
- 引用召回指标必须带协议名。0.098 是 leave-one-out（有时间穿越），
  0.069 是全局时间切分。只说 0.098 等于挑了好看的那个。
- 不能说"RL 在工具门控上有效"。cost=0.8 目前只是 3-seed 均值更高，尚未达到
  预设的 ≥10 seed 推断门槛；而且成本轴人为设定，仿真器证据不等于线上结论。
- 延迟要分清口径：推荐核心当前默认路径约 0.19 ms 是进程内；HTTP 端到端
  5.42 ms / p95 9.67 ms（2026-08-16 WSL/Linux、SQLite@/tmp、c1×200）。
  旧 Windows DeepFM 路径 4.6 ms 是历史数，不再代表默认服务。不要用核心代表 API 性能。
