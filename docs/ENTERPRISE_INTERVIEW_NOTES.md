## 这条扩展可以展示什么

| 展示顺序 | 应用能力 | 可以展示的已有实现 |
|---|---|---|
| 主讲 | 把业务需求变成知识推荐模块 | 根据当前需求筛选有权限、版本有效的资料，排序并返回推荐原因 |
| 辅讲 | 组织接口和业务数据 | MovieLens 页面/API 共用推理核心；企业模块有独立的请求、展示和反馈记录 |
| 辅讲 | 处理失败与服务压力 | 企业排序可降级；MovieLens API 有线程池、限流和监控 |
| 追问 | 验证一次改动是否有效 | 固定种子、相同请求对照、重复反馈回放和测试 |

当前企业部分交付的是排序与回放组件，已有界面/API 属于 MovieLens 路线。
与目标岗位最贴合的下一步，是把企业组件接到现有分析或需求页面，演示“当前需求 → 推荐资料 → 打开或引用 → 记录反馈”。
基于资料生成回答的 RAG、流式输出和企业前后端联动属于后续接入工作。

## 60 秒介绍

> 我做了一个面向企业知识资料的推荐项目，模拟员工看完需求文档或会议分析后，寻找相关历史资料的场景。
> 我用固定随机种子生成的公司、用户、文档和反馈数据，在本地跑通了资料筛选、排序和反馈记录。
> 重点解决三个问题：推荐内容要符合用户权限，文档版本要有效，不同方案要在同一批请求上公平比较。
> 最后做成一条命令就能重复运行的流程，并导出可接入现有企业平台的排序组件。目前完成的是企业场景的离线验证。

## 三个重点，按这个顺序讲

### 1. 先保证资料可以看

同一份资料，可能只对某家公司、某个工作区或某些角色开放。我把权限和文档有效性检查放在排序之前，
保证后续只处理这位用户可以访问的内容。

### 2. 再把相关资料放到前面

先用文本匹配方法找出与当前需求相关的内容，再参考文档新鲜度和历史热度，并减少重复内容。
这样能在用户行为数据较少时先跑通一个容易解释的方案。

### 3. 让结果可以复查

请求、展示和反馈都有对应关系，同一批记录可以重复回放而不重复计数。
比较方案时，让它们面对相同的请求和候选资料；计算历史热度时，只使用当时已经发生的反馈。

## 五个常见追问

**数据是怎么来的，为什么可以用来做项目？**

数据由固定随机种子按业务规则生成，包含公司、角色、文档版本、推荐请求和后续行为。
它适合验证业务流程、做可重复的实验和面试演示；真实用户是否觉得有用，需要后续试点来衡量。

**具体怎么判断资料相关？**

当前用 BM25，可以理解成根据需求与文档中的词语匹配打分，再结合新鲜度和历史热度。
企业侧已经实现这套内容排序；电影推荐模型保留在另一条研究路线中。

**遇到的一个具体问题是什么？**

原种子里两个方案服务的是不同用户，候选资料也不同，平均分差异不能直接归因于方案本身。
我让三种方案回答同一批请求、面对同一组资料，再比较排序结果。

**反馈重复发送怎么办？**

用唯一编号识别记录。编号和内容都相同就不重复插入；编号相同但内容不同就拒绝。
一批记录中途导入失败时，整批撤回，避免只写入一半。

**这和原来的 MovieLens 项目有什么关系？**

MovieLens 用来学习和比较推荐方法，企业场景用来实践权限、版本和业务反馈处理。
复用的是评估和工程方法；企业排序根据文档内容工作，电影用户与电影的模型权重不直接参与其中。

我曾发现，单独评估看起来不错的精排模型，接到召回后反而让整体效果下降。

## 面试前最后五分钟

1. 不看稿讲一遍 60 秒介绍，用一个具体场景开头。
2. 打开一条请求与推荐结果，解释输入、筛选和输出；操作见 [企业种子演练](ENTERPRISE_PILOT_GUIDE.md)。
3. 选一个自己能深入解释的问题：权限先行、公平比较或重复反馈处理。

开发中使用了 AI 辅助。谈到个人贡献时，结合具体代码和实验说明自己的理解、修改与验证过程。
接入细节查 [企业接入说明](ENTERPRISE_RECOMMENDATION.md)，更多指标查 [证据索引](PROJECT_EVIDENCE.md)。
