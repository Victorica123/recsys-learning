# 八股复习地图：视频 / 内容推荐 × AI 全栈

按当前求职目标，先掌握应用链路，再深入模型。每块能讲清“是什么、项目怎么用、出错会怎样”。

## 第一轮：最值得准备的六块

| 项目部分 | 重点八股 | 典型追问 |
|---|---|---|
| 页面与 API | HTTP/JSON、POST 语义、参数校验、OpenAPI、加载与错误状态 | 推荐、曝光与点击怎样对应起来？ |
| 向量推荐 | Embedding、双塔、内积/余弦、Top-K、候选过滤 | 用户和电影怎样匹配，怎样避免重复推荐已评分内容？ |
| 曝光与反馈 | 事务、主键/唯一约束、索引、幂等 | 同一条反馈重试两次，怎样只产生一次效果？ |
| 服务性能 | 同步/异步、线程池、多进程、p95/p99 | 为什么阻塞操作要移出事件循环？增加 worker 有什么成本？ |
| 服务可靠性 | 限流、过载保护、健康检查、日志、模型加载校验 | 请求太多、模型未就绪、权重损坏时分别怎么处理？ |
| 推荐评估 | Recall、NDCG、训练/验证/测试、数据泄漏、基线对照 | 单独模型指标不错，为什么整条链路还可能变差？ |

<details>
<summary>页面与 API：准备到能画出调用关系</summary>

`web/index.html` 负责交互，通过 `POST /v1/recommendations` 调用 `serve.py` 和 `Recommender`。
推荐会写入批次，所以主接口使用 POST。参数不合法返回 400，未知用户返回 404，模型或数据库暂不可用返回 503。
原 `app.py` 是直接调用 Python 核心的 Streamlit 展示，两种入口共享推理实现。
重点理解输入输出、加载中/无结果/失败状态，以及为什么不在多个入口复制推理逻辑。

代码：[web/index.html](../web/index.html)、[serve.py](../serve.py)、[API 契约](../src/api_contract.py)。

</details>

<details>
<summary>向量推荐：先讲清原理和当前实现</summary>

Embedding 是用户或内容的数字表示。双塔分别计算两类向量，再用相似度匹配。
本项目向量经过归一化，内积等于余弦相似度；Faiss 使用 `IndexFlatIP` 做精确检索。
回答时补上候选过滤：用户已评分的电影会被排除，未知用户需要单独处理。

进一步再学负采样和训练损失；大规模近似索引属于拓展知识。
代码：[train_two_tower.py](../src/train_two_tower.py)、[serving.py](../src/serving.py)。

</details>

<details>
<summary>反馈：用事务和幂等解释一条真实工程问题</summary>

一次推荐、实际曝光和用户反馈要能对应起来，模型与策略版本也要保留。
事务保证关联写入的一致性；幂等让成功后的重试不重复产生效果。
本项目使用 SQLite/WAL、事件编号和数据库约束，重复且内容相同的反馈可安全重试，冲突内容会被拒绝。
实际演示可用 `scripts/demo_recommendation_flow.py`：曝光和点击各重复提交一次，最终仍只有 5 条曝光、1 条反馈。

先理解 ACID、主键、唯一约束和索引。MySQL 隔离级别可以继续复习，但不要混淆不同数据库的具体实现。
代码：[feedback.py](../src/feedback.py)，协议见 [反馈说明](FEEDBACK_LOOP.md)。

</details>

<details>
<summary>性能与可靠性：准备三个取舍</summary>

阻塞推理放在线程池里，避免长时间占住事件循环；多个 worker 增加处理能力，也会各自加载模型并占用内存。
请求超过处理能力时，准入保护与限流可以返回 429，调用方按约定退避。
通过客户端延迟、错误、资源占用和健康检查判断运行状态。

重点区分平均延迟与 p95/p99，也区分进程内推理耗时和完整 HTTP 耗时。
代码：[serve.py](../serve.py)、[observability.py](../src/observability.py)，进一步看 [服务说明](PRODUCTION_SERVING.md)。

</details>

<details>
<summary>评估：能用项目中的失败案例说明为什么要对照</summary>

Recall 看相关项找回了多少，NDCG 还考虑相关项排在什么位置。
训练、选方案和最终测试要分开，时间相关任务不能把未来行为带入历史特征。

本项目曾发现 DeepFM 的单独分类指标不错，但接到双塔候选后损害整体推荐效果。
这涉及训练样本与实际候选分布的差异，也说明必须评估最终服务路径。
MovieLens 的评分预测不是广告 CTR；引用数字时带上数据集与切分方法。

证据：[端到端评估笔记](../notes/15-端到端评估与精排重建.md)、[指标索引](PROJECT_EVIDENCE.md)。

</details>

## 第二轮：按岗位或简历内容展开

- **推荐建模**：双塔训练、负采样、FM/DeepFM 特征交叉、AUC/GAUC，再看 SASRec 序列兴趣。
- **应用工程**：鉴权、Docker/Compose、只读模型挂载、持久数据卷、请求追踪与压力测试。
- **强化学习专项**：状态、动作、奖励、探索与利用，以及为什么学习策略可能输给规则。

大模型、RAG 和流式生成可以结合其他 AI 应用经历准备，本项目的默认讲述以内容推荐链路为主。

<details>
<summary>搜索、广告与视频业务怎么继续扩展</summary>

- 搜索面对用户明确输入的查询，需要查询理解、内容索引和相关性排序。
- 广告还需要广告主、出价、预算以及点击/转化等数据，不能直接拿电影评分代替。
- 短视频推荐需要曝光、播放时长、完播、跳过等行为信号，目标和数据口径要随场景重新设计。

本仓库已实现推荐部分。企业知识种子作为独立迁移练习保留，详见 [企业扩展八股对照](ENTERPRISE_STUDY_MAP.md)。

</details>
