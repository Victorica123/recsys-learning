# 11 · 工程化落地：冒烟测试 + 服务化

> 阶段目标：把"能跑出指标的研究代码"推进到"可验证、可部署的工程系统"。
> 本篇记录两件事——**自动化测试体系**与**推荐流水线服务化**，
> 并解释每个技术选择背后的原理与推理。

## 一、为什么这一步是"工程化落地"

前面阶段产出的是**证据**（AUC 0.754、Recall@10 0.097、RL 采样奖励 15.86）。
但证据不等于系统。一个能上线的推荐系统还需要回答三个工程问题：

1. **改动会不会悄悄弄坏核心逻辑？** → 需要自动化测试。
2. **依赖的模型/数据缺了会怎样？** → 需要产物自检与优雅降级，而不是裸崩。
3. **别人怎么调用我的模型？** → 需要一个稳定的服务接口，而不是只有一个 Streamlit 页面。

这一阶段就是把这三点补齐。

## 二、自动化测试体系

### 2.1 技术选型：为什么用标准库 `unittest` 而不是 `pytest`

- 项目 `AGENTS.md` 明确要求"避免引入重依赖"。`research_v2/` 下已有的测试
  （`test_dqn.py` / `test_q_learning.py`）也全部是 `unittest`。
- **推理**：测试框架属于"每个开发者都要装"的基础设施，用标准库能保证
  `git clone` + 建虚拟环境后**零额外安装即可跑测试**。`pytest` 的 fixture/参数化
  虽好，但对本项目的测试规模（几十个用例）收益不足以抵消一个新依赖。
- 一键入口挂在启动 harness 上：

  ```bash
  .venv/Scripts/python.exe scripts/ai_startup_harness.py --test
  # → unittest discover -t . -s tests -v
  ```

  > **踩坑记录**：`unittest discover -s tests`（不带 `-t .`）会把测试当**顶层模块**
  > 导入，跳过包的 `__init__.py`，导致 `src/` 没被加进 `sys.path`。加上 `-t .`
  > 让它以 **`tests` 包**方式发现，`tests/__init__.py` 的路径引导才会执行。

### 2.2 测试分层：纯函数快测 vs 集成慢测

| 层次 | 文件 | 覆盖 | 是否需模型/数据 | 耗时 |
|------|------|------|----------------|------|
| 指标 | `test_metrics.py` | `auc_score` 对拍暴力实现 | 否 | 快 |
| 序列模型 | `test_sasrec.py` | `pad_left` + 因果注意力不变量 | 否（tiny CPU 模型） | 快 |
| RL 环境 | `test_recsim_env.py` | 疲劳/厌倦退出动力学 | 否（stub 用户模型） | 快 |
| 服务打包 | `test_serving.py`（纯函数部分） | `pad_genre_batch` / `check_artifacts` | 否 | 快 |
| 端到端 | `test_serving.py`（集成部分） | 真实双塔+DeepFM 推荐 | **是** | ~8s |

**默认套件：19 个用例 0.31s 全绿，CPU-only、无网络。**
（这是本篇写作当时的数字；套件此后持续扩充，当前值请以
`scripts/ai_startup_harness.py --test` 的输出为准，不要从这里抄。）
端到端集成测试用 `@unittest.skipUnless(os.environ.get("RECSYS_INTEGRATION")=="1")`
门控，避免每次都加载 8s 模型拖慢反馈循环——需要时显式开启：

```bash
RECSYS_INTEGRATION=1 .venv/Scripts/python.exe -m unittest tests.test_serving -v
```

> **原理：测试金字塔**。底层放大量"纯逻辑、毫秒级"的单元测试，顶层放少量"加载真实
> 产物、秒级"的集成测试。快测保护日常重构的反馈速度，慢测在关键节点验证系统真的能拼起来。

### 2.3 三个值得讲的技术点

**(a) AUC 的秩统计实现，用暴力法对拍**

`train_deepfm.auc_score` 没有调 sklearn，而是手写秩统计：
```
AUC = (∑正样本的秩 − n_pos·(n_pos+1)/2) / (n_pos · n_neg)
```
- **原理**：AUC 的概率定义是"随机取一正一负，正样本得分更高的概率"。把所有样本按分数
  排序给秩，正样本秩之和减去"正样本内部两两组合数" `n_pos(n_pos+1)/2`，正好等于
  "正样本得分 > 负样本得分"的**配对数**，除以总配对数 `n_pos·n_neg` 即得 AUC。
- **测试推理**：不能只测 0/1 两个极端。我用一个**暴力两两配对**的参考实现
  （平局记 0.5），在 50 组随机**互不相同**的分数上与手写实现逐一比对。
  分数互异时秩统计与配对计数严格相等——这样测试既独立于实现，又能抓住平局边界的实现差异。
  （顺带验证了 AUC 对分数做**单调变换**不变，因为它只依赖排序。）

**(b) SASRec 的"因果注意力"不变量**

序列推荐的命门是**不能偷看未来**：预测第 t 步只能用前 t 步的历史。
- **原理**：`encode()` 里 `torch.triu(..., diagonal=1)` 造了一个上三角掩码，
  让位置 i 的注意力只能落在 ≤ i 的位置上（因果/单向 Transformer）。
- **测试推理**：与其去读掩码矩阵对不对，不如直接验证**它该有的行为**——
  构造两条只有最后一个 token 不同的序列 `[1,2,3,4]` vs `[1,2,3,9]`，
  在 `eval()`（关 dropout 保证确定性）下编码，断言**前 3 个位置的输出逐元素相等**、
  而第 4 个位置不同。这是"未来不泄漏到过去"的直接行为证据，比检查实现细节更稳。

**(c) 用 stub 用户模型测 RL 环境动力学**

`RecSimEnv` 的用户是冻结的 SASRec（要加载 checkpoint + 数据，很重）。但环境的
**动力学逻辑**（疲劳、厌倦退出）和用户模型是解耦的。
- **推理**：注入一个"每个动作返回固定分数"的 `StubUserModel`，再把 like/dislike 的
  随机硬币换成确定值（`FakeRandom`），就能把环境逻辑单独拎出来做**确定性**断言，
  完全不碰 GPU、checkpoint、数据。
- **验证的两条核心动力学**：
  - **疲劳**：连续推同类型时 `p *= 0.75^(run_len-1)`。固定基础分、强制不喜欢（历史不变→基础分不变），
    观察到 `p` 序列严格按 0.75 等比衰减（0.5 → 0.375 → 0.281）。
  - **厌倦退出**：连续 3 次不喜欢 → 会话提前终止（`done` 在第 3 步变 True，早于 20 步的长度上限）。
  > **原理**：正是这条"同类型疲劳、换类型恢复"的动力学，让**交错推荐**成为最优解，
  > 从而给强化学习创造出可学习的长期优势——也解释了 W3 里"采样部署 15.86 > 贪心 2.81"。

## 三、推荐流水线服务化

### 3.1 重构：把流水线从 Demo 里抽出来（单一事实来源）

改造前，"双塔召回 → DeepFM 精排"的全部逻辑内联在 `app.py`（~110 行）里，
只能被 Streamlit 调用。改造后：

```
src/serving.py   ← Recommender（不 import streamlit 的可复用核心）
     ├── app.py   （Streamlit 展示层，@st.cache_resource 缓存模型）
     └── serve.py （Starlette REST API）
```

- **推理**：展示层（UI）和推理层（模型流水线）职责不同、变化频率不同，必须解耦。
  `Recommender` 不依赖 streamlit，才能在无 UI 的服务进程里加载。`app.py` 从
  "自己算"变成"调 `rec.recommend(user_id, k)`"，删掉了约 60 行重复代码，
  Demo 与 API **保证同源、同结果**。

### 3.2 服务框架：为什么是 Starlette + uvicorn

- 检查依赖发现 `uvicorn 0.51` 和 `starlette 1.3` **已随 streamlit 生态装好**，
  而 `fastapi`/`flask` 没有。
- **推理**：要"零新增重依赖"落地一个 REST 服务，直接用已在环境里的 Starlette（轻量 ASGI 框架）
  最划算。FastAPI 虽然有自动校验/文档，但会引入 fastapi+pydantic 两个新依赖；
  本项目 4 个接口的入参校验手写几行即可，不值得。
- **原理：模型常驻 + 懒加载单例**。模型加载要 ~8s（主要是双塔预计算 3706 个物品向量
  + 建 Faiss 索引 + 读数据），绝不能每请求加载。用进程级单例在**首个请求**（或 `--preload`）
  时构建一次，之后每次推荐只做一次前向 → 毫秒级。

### 3.3 接口与实测指标

| 接口 | 说明 | 实测 |
|------|------|------|
| `GET /health` | 产物/模型加载状态 | `model_loaded=true, n_users=6040, n_items=3706`；未就绪时返回 **503 + degraded** |
| `GET /users?limit=` | 可选用户 ID 列表 | 6040 用户 |
| `GET /users/{uid}` | 画像 + 历史高分电影 | 未知用户 **404** |
| `GET /recommend?user_id=&k=` | Top-k 推荐 | **单次 4.5 ms**（召回 50 → 精排） |

**端到端实测**（ML-1M，CPU）：
- 模型加载：~8 s（一次性，常驻）。
- `recommend(user=1, k=10)`：召回 50 候选 → 精排，返回 10 个**未看过**的有效物品，**9.4 ms**。
- 结果合理性：user 1 的 Top-5 为 Shawshank(0.976)、Silence of the Lambs(0.948)、
  Good Will Hunting(0.945)、It's a Wonderful Life(0.942)、Amadeus(0.938)——高分经典片，符合直觉。

> 这些延迟是"召回+精排"这套两段式架构的核心卖点的量化：Faiss 内积检索把 3706 个物品
> 秒筛到 50（**快**），DeepFM 只对 50 个候选做重打分（**准**）。若让 DeepFM 直接对全库 3706
> 个逐一打分，延迟会放大约 74 倍——这就是工业界"召回→排序"分层的根本原因。

### 3.4 健壮性：把崩溃点全部改成显式降级

服务化的另一半是**永不裸崩**。系统性排查并加固了这些失败路径：

| 失败场景 | 改造前 | 改造后 |
|----------|--------|--------|
| 缺模型权重/数据表 | `torch.load` 抛栈 | `check_artifacts()` 列出缺失文件 + 生成命令；API 返回 **503** |
| 权重损坏/字段错位 | 裸 traceback | `ArtifactsMissingError`/加载异常被捕获降级 |
| 空候选集（用户看遍全库） | `max()` 对空序列抛 `ValueError` | 返回空推荐列表，UI 给友好提示 |
| 召回到映射外物品 / 未知类型 | `KeyError` | 跳过该物品 / 类型退回 0 |
| 未知 user_id | `KeyError` | `UnknownUserError` → API **404** |

> **原理**：服务的每个外部输入（文件、用户 ID、模型输出）都是"信任边界"。工程化的要义
> 是把边界上的每种异常都**显式建模**成"可预期的降级路径"，而不是让它冒泡成 500。

## 五、生产可观测性与压测（2026-07-26）

### 5.1 观测面

- `GET /metrics` 输出进程内请求总量、in-flight、状态码与错误分类，以及每条低基数路由的
  p50/p95/p99/最大应用耗时；指标端点不触发模型加载，也不统计自身，避免探针污染数据。
- 每个业务响应回传 `X-Request-ID` 和 `Server-Timing`；访问日志采用 JSON，路由标签会把
  `/users/任意ID` 归一化成 `/users/{uid}`，且不记录查询串或用户 ID。
- 模型加载记录尝试/成功/失败、耗时和最后错误。懒加载单例增加线程锁，消除了冷启动时
  多个并发请求重复构建 Torch 模型和 Faiss 索引的竞态。
- 所有延迟样本都有上限，不会随运行时间无限占用内存；当前指标按 worker 隔离，多 worker
  生产部署需逐进程采集或换成共享指标后端。

### 5.2 可重复压测

`scripts/load_test_api.py` 只用标准库，每个 worker 复用一条 keep-alive 连接。报告包含压测参数、
客户端端到端延迟、吞吐、状态码、异常、请求 ID 回传校验，以及 `/metrics` 前后计数差；
带 `--tag` 的报告拒绝覆盖已有实验。

本机单 Uvicorn worker、CPU、固定调用
`GET /recommend?user_id=1&k=10` 的结果：

| 并发 | 请求 | 吞吐 | p50 | p95 | p99 | 错误 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 200 | 285.845 RPS | 3.436 ms | 4.301 ms | 4.476 ms | 0 |
| 16 | 500 | 291.192 RPS | 53.048 ms | 59.966 ms | 96.839 ms | 0 |
| 64 | 1000 | 293.935 RPS | 139.137 ms | 185.898 ms | 1733.937 ms | 0 |

三个报告的服务端计数增量分别精确等于 200、500、1000，且请求 ID 回传失败均为 0。
另外实际触发了 400 和 404，`/metrics` 正确归入 `invalid_request` 与 `not_found`。

> **2026-08-16 补记**：上表走的是已下线的 DeepFM 精排路径。当前默认双塔 Top-K
> 在 WSL/Linux CPU、SQLite 位于本地 `/tmp` 时复测为 HTTP mean 5.42 ms /
> p95 9.67 ms（c1×200），推荐核心 0.19 ms；SQLite 放在仓库目录所在的 `/mnt/d`
> 会因跨文件系统写放大到约 30 ms，不是服务逻辑退化。产物：
> `experiments/serve_load_default-retrieval-linux-c1-tmpdb-20260815.json`。

### 5.3 结论与下一步

吞吐从并发 1 到 64 只从约 286 增至 294 RPS，说明单 worker 的 CPU 推理能力在约
290 RPS 附近饱和；继续堆并发主要形成排队，尤其并发 64 的 p99 已到 1.73 s。
如果目标是 p99 < 100 ms，当前单 worker 应把并发控制在约 16 以内。

服务端中间件的计时从请求进入 ASGI 应用开始，不含 Uvicorn 事件循环之前的排队；因此
高负载下 `/metrics` 的应用耗时明显低于客户端端到端耗时是预期现象。容量/SLO 决策应以
客户端报告为准，并把下一轮工程工作放在：

1. 先做 2/4 worker 的扩展曲线，确认吞吐是否近线性以及内存放大（每 worker 一份模型）。
2. 在入口增加 in-flight 限流/过载保护，避免请求无界排队导致秒级尾延迟。
3. 接入跨 worker 指标聚合与事件循环滞后监控，再定义正式告警阈值。

### 5.4 续作结果：多 worker 与过载保护

前两项已于 2026-07-26 完成。同步的 Torch/Faiss 推理被放入线程池，业务请求进入
`AdmissionControlMiddleware`；超过每 worker 上限时立即返回 `429 + Retry-After`。
`/health` 和 `/metrics` 不占准入槽，热健康检查也不再竞争推理线程池。

同一台 Windows 主机（12 逻辑核）、ML-1M、每点 600 请求，在并发 16 下：

| workers | 成功吞吐 | HTTP 200 p99 | 进程 RSS |
|---:|---:|---:|---:|
| 1 | 159.8 RPS | 148.8 ms | 887.6 MiB |
| 2 | 270.1 RPS | 72.4 ms | 1778.2 MiB |
| 4 | 385.5 RPS | 51.9 ms | 3547.8 MiB |

2/4 worker 相对单 worker 的吞吐为 1.69x/2.41x，但内存近似严格变成 2x/4x。
4 worker 在并发 32 时达到 475.4 RPS、p99 81.9 ms；并发 4 的单点曾达到
630.6 RPS，但 keep-alive 连接分配与本机 CPU 调度会造成波动，容量规划应采用同并发
对照并在目标环境重复多轮。

并发 64 的准入阈值扫描表明：

| max in-flight | 成功 RPS | HTTP 200 p99 | 429 比例 |
|---:|---:|---:|---:|
| 4 | 117.8 | 197.3 ms | 94.2% |
| **8** | **132.4** | **340.8 ms** | **88.8%** |
| 16 | 146.6 | 481.9 ms | 75.3% |
| 32 | 140.3 | 806.1 ms | 50.7% |
| 256（近似关闭） | 148.6 | 869.6 ms | 0% |

闸门 8 保留了宽闸门约 89% 的成功吞吐，同时把成功请求 p99 降低约 61%，因此作为
本机默认起点；它不是通用常数，必须按实例 CPU、worker 数、流量形态与 SLO 重调。
极端突发下单 worker 没有任何阈值守住 100 ms，说明准入闸门只能“止损”，不能替代
多 worker、入口限流和容量扩展。

证据：

- `experiments/serve_scaling_verified-20260726.json`
- `experiments/serve_scaling_overload-gates-verified-20260726.json`
- `figures/serve_worker_scaling_verified-20260726.png`
- `figures/serve_overload_gates_verified-20260726.png`

原“下一步”中的 1、2 已完成；剩余重点是跨 worker 指标聚合、事件循环/CPU 指标，以及
入口层的速率限制或有界等待队列。

### 5.5 最终收口：跨 worker 运维面

剩余本机可完成项也已落地：

- `/live` 与 `/ready` 明确拆分存活/就绪，且不触发模型加载；
- 每 worker 发布有界原子快照，`/metrics/aggregate` 合并新鲜 worker，
  `/metrics/prometheus` 输出可直接抓取的文本；
- 请求指标新增 10/60 秒 QPS，路由延迟按 HTTP 状态拆分，避免快速 429 掩盖
  成功请求 p99；
- 运行时采样 CPU、当前 RSS、事件循环 lag；
- 令牌桶按每 worker 控制平均速率/突发容量，并把 `rate_limited` 与
  `overloaded` 分开计数；
- 过期 worker 和半写入临时文件自动回收；正常 lifespan 停机等待后台写完成后再注销；
- 提供 Prometheus 告警规则和完整生产运行手册。

最终真实模型、2 worker 验收（`serve_production_smoke_final-v2-20260726.json`）：

| 阶段 | 结果 |
|---|---|
| 低速流量 | 40/40 成功，客户端 p99 7.151 ms |
| 并发 32 突发 | 27 个 200、273 个 429，成功请求 p99 88.740 ms |
| 聚合一致性 | 340 个业务请求精确对齐，两个 worker 均处理到流量 |
| 运维信号 | Prometheus、CPU、RSS、事件循环 lag 全部存在 |
| 清理 | 正常生命周期和强制崩溃恢复路径均无注册文件残留 |

这意味着**单机服务代码层面的生产缺口已经收口**。无法在本仓库内替代的外部能力包括：
TLS/身份认证、跨主机全局限流、真正的 Prometheus 服务、反向代理/负载均衡、编排平台
滚动发布，以及真实网络和线上流量 SLO；对应接入约定已写入
`docs/PRODUCTION_SERVING.md`。

## 六、真实反馈最小闭环（2026-07-27）

### 6.1 从“能记录”到“能做决策”

第二版增加 `feedback_app.py`，让真人用匿名代号对每批推荐选择想看、喜欢、
不喜欢或跳过。行为策略采用显式 epsilon slate 探索，默认 10%，而不是给
确定性 Top-K 伪造 propensity。

候选策略固定为 DeepFM 分数加类型多样性奖励。正式报告按推荐批次配对比较
DeepFM Top-K 与候选策略的 item-inclusion IPS，并用 bootstrap 给出差值的 95%
置信区间；bootstrap 以匿名体验者为 cluster。门槛为 200 批推荐、5 位体验者、
95% 曝光覆盖率、ESS 100 和完整支持；任何一项不足都只返回
`collect_more_data`。隔离 UI 冒烟的 1 批数据被正确拦截，证明
决策门槛生效，但不构成候选策略收益证据。

为避免单人逐项点击成为采集瓶颈，页面后来增加了默认的快速个人试验：每批只需
点击一次完成五选一，系统把被选项记录为 `click`、其余展示项记录为显式 `skip`，20 批后
自动停止。快速模式与正式模式使用不同的策略名，并且只纳入当前体验者完整提交的
批次；它提供的是 90% 区间下的个人方向性信号，不应外推为总体策略结论。
